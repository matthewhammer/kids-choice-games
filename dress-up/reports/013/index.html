Dress Up in Hazel: the hard part of the drawing is what runs every frame, the music can be computed, and the menus need a layout Hazel lacks

Matthew asked three questions about porting Messed Up Dress Up to Hazel (ticket 402): which parts of the drawing would be hardest for Hazel, whether Hazel can do music, and how to offer the game's menus in Hazel while keeping to Always Be Knolling. He also asked for the game's advanced features, staged as challenges. It builds on ^du_report(8) (the port, piece by piece), ^du_report(5) (the menu rules) and ^report(15) (the game and its livelits, measured side by side). The game at 0.0.334; Hazel on its livelits × modular editors branch (hazelgrove/hazel#2635) at 90ed4505bf.

Short answers.

  1. The drawing's hard part is not its SVG but what runs around it. A Hazel view can draw every element the game uses (41 SVG element kinds, gradients, clips, masks, filters and animations included). What Hazel lacks is what the game does at run time: motion every frame (a livelit has no clock, and a change costs 0.13 to 1.09 s against a frame's 16.7 ms), measuring the drawn picture (about 100 calls place things on it), its sizes (the greenhouse has 1,906 elements; the largest Hazel picture so far, 570 shapes), and byte-exact numbers: Hazel's to_fixed and the game's f1 disagree on 5 of 7 values tried.
  2. Music: Hazel can compute it today; playing it takes a JS player or a new builtin. 63% of the game's music code is pure (the tunes, chords, arrangements and the score of note events). A Hazel program computed a 1,216-event score, the size of the forest tune's, in about 0.2 s. A livelit cannot make a sound; Hazel's MVU apps can, a sine beep (Cmd.PlayTone) with timers, which corrects ^du_report(8)'s "no sound binding".
  3. The menus: Hazel meets about two of the nine knolling rules, and the gap is a layout, then speed. Livelits show up inline, stacked in the UX outline, or in a sidebar column; none is a grid of named boxes. The plan: the settings as a tree of modules, a "knolled" UX layout that draws modules as tabs and their members as boxes, and big livelits for the bespoke designers. Even laid out right, each change costs 0.13 to 1.2 s; the rule "keep it fast" waits on Hazel's speed.
  4. The advanced features fall into six stages, from pictures Hazel can draw today, through small builtins, a clock for livelits, interaction inside the picture and the designers, to the whole game at 60 fps, which waits until a change costs about 16 ms.

3. The menus, knolled, in Hazel

The nine rules of Always Be Knolling (^du_report(5)), and how Hazel's livelits measure up today:

RuleHazel today
A box for each thing you can see or hear, named onceMisses: a UX cell is headed by the binding's name, the Projectors card by printed syntax
Nesting by boxes aloneMisses in the UX outline (a flat stack); nested livelits could do it
Knolled: a grid, things of a kind the same sizeMisses: a stack or a column
A row on one lineMeets, for a slider
Show the thingMeets: views draw pictures
One decision, one placePartly: one binding, but a box cannot be shown in two places
Mirror the picturePartly: the picture can be a UX cell, not a sticky first card
The same at every scaleMisses: three different layouts
Keep it fastMisses: a change costs 0.13 s (Kids' Choice) to 1.2 s (Full Body in the UX outline), against Dress Up's 1.4 ms

The options

OptionWhat it gives, and what it costs
One big livelit whose view is the menuFull control of tabs, grids and pictures; but its open tab and folds live in its model, so every click is an edit (and an undo step) costing about a second; good for bounded designers (the world grid, the castle map, the mixer)
A knolled UX layoutModules as tabs, their members as boxes in a grid, the picture as a sticky first card, tab and fold state kept by the editor, not in the program: meets rules 1, 2, 3 and 8, partly 7
The program organized as the menuA module per tab and a submodule per box, each setting a livelit; works with today's UX outline, but only as a flat stack
An MVU app in the sidebarFast, but its state is not program text, so the program cannot read the settings: rewriting the game as an app

The plan: The program organized as the menu, with a knolled UX layout over it, and big livelits for the bespoke designers: as the game itself has generic boxes for most tabs and its own full screens for music, the world and the castle.

What next

  1. Port the face alone (431 lines) and time it, as ^du_report(8) proposed; add an f1-like builtin first, so the picture can be compared byte for byte.
  2. Port the forest tune's score: compare its events one by one with the game's songOf("forest"), then play them through the game's own instruments from JSON.
  3. Try a view with an <audio> of the archive's recording, the cheapest sound in Hazel today.
  4. Prototype the knolled UX layout on one tab (the friend's face): modules as boxes, the picture as the first card.
  5. Ask the Hazel team about a clock (a subscription) for livelits: it unlocks stage 3 and most of stage 4.
