Piece by piece

How could all of Messed Up Dress Up's current features move to Hazel, piece by piece: what would two months of work bring over, what would three, and what has to be decided first? The game at 0.0.289: 26 script parts, 22,407 lines, 289 versions since 2026-10-12, 130 checks. A plan, not a measurement: every number about Hazel here is from earlier measurements, cited.

Short answers.
  1. In two months, what the game draws; not the game. About 56% of the code is pure: settings in, a picture out (the friend, the poses, the places). That ports piece by piece, and each piece can be checked exactly: the picture archive holds the game's own SVG for every place, costume and pose, with the settings that made it, so a Hazel piece is done when the same settings give the same SVG.
  2. In three months, also the rules: what is in the way, planned walks, the tunes as data, the world designer and the first settings as livelit GUIs. The frame loop, the controllers and the sound would still be JS.
  3. The runtime waits on Hazel, not on time. A frame at 60 a second has 16 ms; a livelit release is 0.13 to 0.5 s today (from 4.6 s at the start of the month). Hazel lacks a clock, a sound binding and a way to measure a drawn picture. So the plan keeps JS as the engine and makes Hazel the source of the pictures, as a livelit's view is.
  4. Measure before believing either schedule: port the face alone (431 lines) and time it, in week 1.
  5. Decide first what "ported" means: the same picture from the same settings (checkable now), or the whole game running in Hazel (not reachable in three months).

What Hazel has, and lacks

  • User-defined livelits: init, view and update, with splices (splice_new, splice_set, splice_eval): a livelit's model and its GUI, in the editor (integration branches, hazelgrove/hazel#2597 and #2635; not on dev)
  • The Livelit Playground: slides already port pieces of the friend from this game: Polygons, Shirt and Pants, Shoes and Hair, Kids' Choice, the 1990s Face; each a picture built as SVG text from a model
  • Pictures as values: SVG is text Hazel can build: floats with +. and friends, to_fixed for numbers, strings, lists of shapes drawn in order
  • Types: records, labelled tuples, sums, System F over values (typfun, explicit @<T>); Modules II for libraries. No type application (no M(a) for a type constructor M)
  • Speed: a livelit release about 0.13 to 0.5 s on the faster branch (#2635) after this month's work (from 4.6 s), against under a millisecond for this game to draw the friend and 16 ms for a frame at 60 fps

What to decide first

  • What "ported" means: draws the same picture from the same settings (the oracle can check it), or runs the whole game in Hazel (needs a clock, input and sound Hazel lacks).
  • Where the Hazel code lives: Playground slides, one piece each, or a library module and one program; slides cannot import each other yet.
  • Which version to port: a frozen one, with the changes after it logged, or the moving game.
  • Who plays the Hazel version: the children, in the editor, or only the archive's oracle until the pieces join.

What next

  1. 1. Decide what ported means: the oracle (same settings, same SVG) or the whole game; this report assumes the oracle for two months.
  2. 2. Measure first: port the face alone (03 face, 431 lines) and time a release of its view in Hazel, before any schedule is believed.
  3. 3. Compute boxes from geometry: move collision boxes from DOM measuring into the drawing functions in the JS game first (it helps the game, and makes the port pure).
  4. 4. Freeze a version: tag the version to port (dress-up-0.0.289) and keep a log of what changes after it.
  5. 5. One program per place: try the empty room, bubble space and the tent as three small programs sharing the settings types.
  6. 6. Keep the JS as the engine: the frame loop, input and sound stay JS; Hazel supplies the pictures, as a livelit's view does.
